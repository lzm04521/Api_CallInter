# 设计文档 — API 定时保活工具（ApiCallInter）

- 日期：2026-08-24
- 状态：待用户评审

## 1. 背景与目标

运维人员通过 VPN 访问多个客户/项目环境，VPN 隧道或网关会话因长期无流量而空闲超时、自动断开。本工具对多个运维项目各自配置一组 API 接口，按项目级定时策略自动发起 HTTP 请求产生流量，保持 VPN 会话活跃，并记录每次请求结果，便于排查"VPN 什么时候断的"。

### 1.1 功能概览（一期）

- **多项目管理**：每个运维项目独立配置名称、备注（VPN 信息等）、请求间隔、随机抖动、启用开关
- **接口管理**：每项目挂多个 API 接口（URL / 方法 / Headers / Body / 超时 / 启停），支持静态 token（写 Headers），每接口可手动"立即请求"
- **定时调度**：项目级间隔 + 随机抖动（避免固定间隔的机器特征被安全设备识别），程序启动即执行首轮，配置变更热生效
- **请求历史**：每次请求的状态码 / 耗时 / 错误信息落库，按项目 / 接口筛选分页，按保留期自动清理
- **托盘常驻**：系统托盘图标，双击或菜单打开 Web 管理页，可勾选开机自启，单实例保护
- **Web 管理页**：概览（项目状态、下次执行倒计时、最近结果、运行时长与内存）/ 项目与接口维护 / 日志查询 / 系统设置 / 关于与升级
- **系统设置**：管理页内修改监控端口（重启程序生效，可一键重启）、开机自启开关（即时生效）
- **关于与升级**：显示当前版本，检查 GitHub Release 新版本，应用内一键升级（下载 → 替换 → 自动重启）
- **绿色部署**：self-contained zip，GitHub 打 tag 自动出包，覆盖即更新，无部署脚本

### 1.2 质量目标

- **7×24 无间断运行**：任何单次网络错误、请求异常、DB 写入失败都不得导致进程退出；调度循环异常自恢复（详见第 11 节）
- **内存稳定**：长时间运行内存无持续增长——连接复用、DbContext 短生命周期、日志与历史记录增长受控；概览页暴露运行时长与内存占用，便于长期观察（详见第 11 节）
- **可观测**：文件日志（程序运行）+ 请求历史（业务结果）双层记录，问题可回溯

### 1.3 成功标准

- 多项目、多接口配置，项目级独立定时策略，可单独启用/停用
- 系统托盘应用形态，支持开机自启，从托盘打开 Web 管理页
- Web 管理页可完成全部配置与查看请求历史
- 发布物为绿色自包含目录，GitHub Release 出包后下载替换即完成更新，无部署脚本

## 3. 整体架构

单一 ASP.NET Core 进程，三类职责共存：

```
┌──────────────────────────────────────────────────────┐
│ ApiCallInter.exe（系统托盘应用 + 内嵌 Web 服务）       │
│                                                      │
│  WinForms 托盘 NotifyIcon：打开管理页/开机自启/退出    │
│  SchedulerService   ← BackgroundService，定时调度     │
│  ApiInvoker         ← HTTP 执行器，写请求日志          │
│  Minimal API /api/* ← 管理接口                        │
│  wwwroot/           ← Vue3 管理页（自托管静态资源）    │
│                                                      │
│  SQLite: %ProgramData%\ApiCallInter\app.db            │
│  文件日志: %ProgramData%\ApiCallInter\logs\           │
└──────────────────────────────────────────────────────┘
```

| 决策点 | 选择 | 理由 |
|---|---|---|
| 框架 | .NET 10（LTS）+ ASP.NET Core Minimal API | 本机 SDK 已就绪；Minimal API 代码量最小 |
| 托盘 UI | WinForms `NotifyIcon` + `ApplicationContext`，主线程消息循环 + 后台 `WebApplication.RunAsync()` | 标准库实现托盘图标与菜单，不引第三方库 |
| 调度 | 单个 `BackgroundService` 内存计划表 + `PeriodicTimer` 轮询 | 固定间隔循环足够，不引入 Quartz/Hangfire |
| ORM | EF Core + `EnsureCreated()` 自动建表 | 3 张表 CRUD，个人工具不做迁移演进 |
| 文件日志 | Serilog 滚动文件（程序运行日志，与业务请求历史分离） | 排查服务启动/调度异常用 |
| 前端 | `wwwroot/` 内嵌 Vue 3（**自托管 vue.global.prod.js**，不用 CDN） | 运维服务器可能无外网，必须离线可用 |
| HTTP | `IHttpClientFactory` | 标准 socket 耗尽防护 |

## 4. 部署与更新

### 4.1 发布物

`dotnet publish -c Release -r win-x64 --self-contained`，产物为绿色目录 zip（含运行时，目标机无需装 .NET），由 GitHub Actions 在打 tag 时自动构建并上传 Release 附件。

### 4.2 运行与托盘交互

- 双击 exe 即运行：无主窗口，常驻系统托盘
- 托盘菜单：**打开管理页**（调默认浏览器打开 `http://localhost:{当前端口}`，双击图标同效）、**开机自启**（勾选项）、**退出**
- 单实例保护（命名 Mutex）：重复启动时不再创建托盘，直接打开管理页后退出
- 托盘图标：程序内用 System.Drawing 简单绘制，不依赖外部图标资源

### 4.3 开机自启

托盘菜单勾选"开机自启"时写用户级注册表 Run 键（`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，名称 `ApiCallInter`，值为 exe 全路径），取消勾选即删除。无需管理员权限，不使用服务方式自启。

### 4.4 更新流程

托盘菜单退出程序 → 用 Release zip 覆盖程序目录 → 双击启动。数据在 ProgramData，不受影响。

### 4.5 GitHub 发版

新增 `.github/workflows/release.yml`：push tag `v*` 触发 → build（`-p:Version` 从 tag 注入程序集版本）→ 打包 self-contained zip → 创建 GitHub Release 并附 zip。与现有 git-release 工作流衔接（打 tag 即出包）。

### 4.6 应用内更新

- **检查更新**：调用 GitHub Releases API（repo 默认 `lzm04521/Api_CallInter`，appsettings 可配），比对程序集版本与 latest tag，返回新版本号与更新说明；网络失败明确报"检查失败"
- **一键升级流程**：应用内下载 Release zip → 解压到 `%ProgramData%\ApiCallInter\updates\<version>\`（失败清理残留）→ 用户确认重启 → 启动独立 PowerShell updater：等待旧进程退出 → 复制覆盖程序目录（运行中的旧 exe 先改名 `.old` 再替换）→ 启动新版本 → 清理 `.old` 与 updates 目录 → 全程写 `logs\update.log`
- **兼容手工更新**：不点一键升级仍可走 4.4 手动覆盖流程；程序启动时检测 updates 目录残留并清理（不自动续装，失败可见）
- 程序目录需可写（绿色目录部署默认满足）；权限不足时 updater 记日志报错，原版本不受影响

## 5. 数据存储设计

数据库：`%ProgramData%\ApiCallInter\app.db`（SQLite，EF Core `EnsureCreated()` 首次启动自动建库）。支持环境变量 `APICALLINTER_DATA_DIR` 覆盖数据目录（开发调试指向本地目录，避免开发态写 ProgramData）。

> 结构演进策略：一期不做 EF 迁移，结构变更时删库重建、重新录入配置；如后续配置量变大，再补导出/导入。

### 5.1 表结构

### 5.2 日志清理

保留期默认 90 天（appsettings 可配）。服务启动时与每日 00:00（本地时间）各清理一次 `RequestedAt` 超期的记录。按 20 接口 × 5 分钟间隔估算约 5,760 条/天，清理保证库体积稳定。

## 6. 调度设计（SchedulerService）

- 单个 `BackgroundService`，内存维护计划表：`{ ProjectId, IntervalSeconds, JitterMs, NextRunAt, Running }`
- 主循环 `PeriodicTimer(500ms)`：到期且 `Running=false` 的项目触发执行（fire-and-forget，`Running` 标志防重入；上轮未完成则本轮跳过并记文件日志）
- **间隔与抖动**：每轮触发后按 `NextRunAt = 本轮触发时间 + IntervalSeconds ± Random(0, JitterMilliseconds)`（正负均匀随机）排下一轮。校验层保证 `0 ≤ Jitter < IntervalSeconds × 1000`，间隔恒为正，无需额外 clamp
- **启动行为**：服务启动后各启用项目立即执行首轮（重启后马上确认连通性），之后按"间隔 ± 抖动"循环
- **配置变更**：Web API 增删改项目后调用调度器 `Reload()`，从 DB 重读；存量项目与新项目统一 `NextRunAt = now + 新间隔 ± 新抖动` 重新起算
- **执行顺序**：项目内所有启用接口并行请求（`Task.WhenAll`），单接口超时不阻塞其他接口

## 7. HTTP 请求执行（ApiInvoker）

- `IHttpClientFactory` 命名客户端，每接口独立超时（克隆 HttpRequestMessage 或 per-request `CancellationTokenSource` 实现超时控制）
- 请求结果逐条写入 `RequestLogs`（成功与失败都写）
- 异常分类记录：`TaskCanceledException`（超时）、`HttpRequestException`（DNS/连接/SSL）、其他异常，摘要入 `ErrorMessage`，不吞异常不上报假成功
- 手动"立即请求"与定时触发共用同一执行路径，不影响该项目的定时计划

## 8. Web API 设计（前缀 `/api`，JSON）

| 方法与路径 | 说明 |
|---|---|
| GET/POST/PUT/DELETE `/api/projects`（及 `/{id}`） | 项目 CRUD |
| GET/POST/PUT/DELETE `/api/projects/{id}/endpoints`（及 `/{eid}`） | 接口 CRUD |
| POST `/api/endpoints/{id}/invoke` | 手动立即请求，返回本次结果 |
| GET `/api/logs?projectId=&endpointId=&page=&pageSize=` | 请求历史分页，默认按时间倒序 |
| GET `/api/overview` | 首页概览：各项目启用状态、下次执行时间、各接口最近一次结果、运行时长与内存占用 |
| GET/PUT `/api/settings` | GET 返回监控端口、自启状态（注册表实读）、当前版本；PUT 保存端口，变更时返回 `needsRestart=true` |
| POST `/api/settings/autostart` | 写/删注册表 Run 键（4.3），即时生效 |
| POST `/api/app/restart` | 立即重启程序（停 Host → 重新拉起进程），配合端口变更生效 |
| GET `/api/update/check` | 调 GitHub Releases API 比对版本，返回 `hasUpdate`、新版本号与更新说明 |
| POST `/api/update/prepare` | 下载最新 Release zip 到 `ProgramData\updates\` 并解压校验，返回就绪（4.6） |
| POST `/api/update/restart` | 启动 updater 完成文件替换并自动重启（4.6） |

校验规则：Url 必须 http/https 绝对地址；`IntervalSeconds >= 30`；`JitterMilliseconds >= 0` 且 `< IntervalSeconds × 1000`；`TimeoutSeconds` 1~120；Method 限枚举；`WebPort` 1024~65535。校验失败返回 400 + 明确 message。

## 9. Web 管理页（`wwwroot/`）

单页应用，`index.html` + Vue 3（vue.global.prod.js 放入 `wwwroot/vendor/` 自托管，**不依赖外网 CDN**）+ 原生 fetch，无构建链。三个 Tab：

1. **概览**：项目卡片（启用状态、下次执行倒计时、最近一次请求成败），项目级启停开关
2. **项目管理**：项目增删改（名称/备注/间隔/抖动/启停）；展开项目编辑接口列表（URL/方法/Headers/Body/超时/启停），每接口"立即请求"按钮 + 结果提示
3. **请求日志**：按项目/接口筛选 + 分页表格（时间、状态码、耗时、错误）
4. **系统设置**：监控端口修改（保存后提示需重启，提供"立即重启"按钮）；开机自启开关（与托盘菜单勾选项同一注册表真源，状态一致）
5. **关于**：当前版本号、检查更新（显示新版本号与更新说明）、一键升级（准备更新包 → 重启完成升级）、GitHub Release 页链接

无登录页、无 session（一期明确不做）。

## 10. 端口与监听

- 默认 `http://127.0.0.1:61121`（托盘应用默认仅本机管理；一期无鉴权，不对内网暴露）。端口可在设置页修改（存 `AppSettings` 表，重启程序生效）；监听 host 由 appsettings `Urls` 控制，需要远程管理时可改为 `0.0.0.0`
- 风险说明：一期无鉴权，一旦监听 0.0.0.0，同网段可达者均可查看/修改配置并借本机发起请求，**仅限可信内网使用**；如需对外暴露，二期加访问口令

## 11. 错误处理与 7×24 健壮性

### 11.1 错误处理

| 场景 | 行为 |
|---|---|
| 接口请求失败/超时 | 记 `RequestLogs`（Success=false + ErrorMessage），不重试（保活场景下轮自然重试） |
| 调度循环异常 | 循环内 catch-all：记录文件日志并继续下一轮 tick；`ExecuteAsync` 永不因单次异常退出（避免 .NET 默认的 BackgroundService 异常停掉整个 Host） |
| DB 写日志失败 | 记文件日志（Serilog），不影响调度 |
| 未捕获异常 | `AppDomain.UnhandledException` / `TaskScheduler.UnobservedTaskException` 全部记录文件日志，进程尽量存活 |
| 服务启动建库失败 | 启动失败：托盘气泡提示 + 文件日志写明原因 |
| 配置 API 校验失败 | 400 + message |
| 打开浏览器/写自启注册表失败 | 托盘气泡提示 + 文件日志，不影响主流程 |

### 11.2 资源与内存管理

- EF Core `DbContext` 短生命周期：每轮调度 / 每次 API 请求一个 scope，不做长持有
- `HttpClient` 经 `IHttpClientFactory` 复用连接池，避免端口耗尽与句柄泄漏
- 增长源全部受控：`RequestLogs` 按保留期清理（5.2）、Serilog 滚动保留 30 天、调度计划表随 `Reload()` 重建，不使用无界集合
- WinForms 侧：`NotifyIcon` / 菜单 / 图标在退出时释放，事件订阅随 Context 销毁
- GC 策略：默认 Workstation GC（并发），托盘工具内存占用小、够用；概览页显示进程运行时长、Working Set、托管内存（`GC.GetTotalMemory`），便于长期观察内存曲线是否平稳，有数据后再决定是否调整 GC 配置

## 12. 测试与验证

- 单元测试（xUnit）：调度计划计算（到期/防重入/Reload 重算/抖动抽样落在 ±Jitter 范围且边界正确）、ApiInvoker 成功/超时/网络异常分类与日志落库（mock HttpMessageHandler + SQLite 内存库）、日志清理、设置读写与端口校验、更新检查版本比对与 Release 解析（mock GitHub API 响应）
- 集成验证：`dotnet build` + `dotnet test` 全过；本地控制台起服，用 `https://httpbin.org` 类公开接口或本地测试端点配置一个项目，观察定时请求与历史记录
- 部署验证：托盘勾选开机自启后重启机器验证自启、单实例重复启动行为、覆盖更新后数据仍在

## 13. 范围外（二期预留）

- Windows 服务形态（服务器上无人登录 7x24 运行；托盘应用需要保持用户登录会话，纯服务器场景如成为主需求再做双宿主）
- 动态登录换取 token/cookie 再请求
- 连续失败 N 次告警（企业微信 webhook 等）
- 管理页访问口令
- 配置导出/导入、数据库结构迁移
- 增量更新包（一期升级包为全量 zip）
